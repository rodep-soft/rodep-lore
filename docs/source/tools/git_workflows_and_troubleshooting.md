# Gitワークフローとチーム開発：泥臭いトラブルシューティングと運用思想

チーム開発におけるGitの運用ルール、Pull Request (PR) の捌き方、そしてありがちなコンフリクトやミスに対する実践的なトラブルシューティングを高密度にまとめた。

## 1. チーム開発におけるコミットとPRの哲学

### 1.1 コミットは細かく、早めに投げる
「面倒かもしれんけど、今後なるべくcommitは切ってgithubに上げてほしい」「なるべく刻んどいて終わったらcloseしていくこと」
ローカルで数千行、数万行のコードを溜め込み、一度に巨大なPRを出す（通称：メガPR）ことは、レビューアの負荷を極端に高め、マージ時のコンフリクト地獄を招く。
- **ghコマンドの推奨**: GUIツールやブラウザの操作が面倒であれば、GitHub CLI (`gh`) を用いてターミナルから直接PRを作成・管理する運用が推奨される。

### 1.2 Issueとの連動
バグ修正や新機能の追加は、まずIssueを立て、そこに進捗や変更点を細かくコメントとして残すことが重要である。
- *「進捗あったり何か変わったりしたらコメント追加しとくといいよ。見なかったら結局あまり意味はないから」*
IssueとPRをリンクさせ、PRがマージされた瞬間にIssueが自動的にクローズされるフロー（`Fixes #XXX` などの記述）を徹底することで、タスクの迷子を防ぐ。

## 2. 泥臭いトラブルシューティング：やってしまった時の対処法

### 2.1 不要なファイルの誤コミット（build/, log/ など）
10,000行を超えるようなPRの大部分は、コンパイル成果物（`build/` や `install/`ディレクトリ）を誤ってコミットしてしまったことに起因する。
- **対処法**: 「やばいの上げちゃうことは僕でもあるけど、`git rm` すればいいからね」
慌てて手動でファイルを消すのではなく、`git rm -r --cached <dir>` コマンドを使用して、Gitのトラッキング対象からのみ外し、その状態を再度コミットしてPushする。
- **予防線 (`.gitignore`)**:
  - `**/build/` のように冗長に書く必要はなく、`build/` とシンプルに記述する。
  - プロジェクト初期段階で `.gitignore` を完璧に揃え、いち早く `main` ブランチにマージしておくことが、チーム全体の誤コミットを防ぐ最大の防御策である。

### 2.2 パッケージリストの自動トラッキング
「aptの手動でインストールしたpkgはcommitのタイミングで自動で記録されるはず」
Dockerfileを使わないローカルビルド環境の場合、新しい依存パッケージをインストールした事実が他の開発者に共有されない問題が発生する。コミットフック（Pre-commit hook）等を活用し、システムにインストールされたパッケージ一覧（`package.txt` など）を自動生成してリポジトリに含める工夫が必要である。

## 3. レビューとCIの連携

### 3.1 レビューアへの配慮と自動化
「コードについては書き途中だろうしあえて言及しないけど…」
WIP (Work In Progress) な状態であってもPRをオープンにすることは推奨される。しかし、その際は明確に `Draft PR` として扱うべきである。
- CI（GitHub Actions）が通っていないPRは、人間のレビューアがコードを見る前に弾くべきである。
- *「何も考えずにMergeするのは…あまりPull Requestを出す意味がなくなってしまうからね...笑。個人的にはもう目的がCIのチェックをするってだけになってるし」*
「CIがグリーンであること」がマージの最低条件であり、CIの自動テストが人間の目視レビューを代替、あるいは強力に補完するシステムとなっている。

## 4. 運用ルールのまとめ

1. **こまめにPushする**: ローカルに溜め込まない。
2. **.gitignoreは絶対**: プロジェクト作成直後に設定し、絶対に成果物をコミットしない。ミスしたら即 `git rm -r --cached`。
3. **CIを信じる**: PRはCIを回すためのトリガー。エラーが出たら別ブランチで直し、PushしてCIを通す。
4. **CLIの活用**: `gh` コマンドやシェルエイリアスを駆使し、Git操作の手間を極限まで減らす。
