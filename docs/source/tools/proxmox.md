# Proxmox

## Proxmox VEによる仮想化基盤とネットワーク設計

ローカルマシンのリソース制限から解放され、より本番環境に近い複雑なインフラストラクチャを模倣するためには、専用の仮想化サーバーを構築することが次のステップとなります。オープンソースのプラットフォームであるProxmox VEは、KVMベースの仮想マシン（VM）とLinuxコンテナ（LXC）を単一のインターフェースで統合管理でき、高度な開発環境の基盤として非常に優れています。

### 軽量コンテナと完全仮想マシンの使い分け

Proxmox上で環境を構築する際、VMとLXCの適切な使い分けがシステム全体の効率を左右します。カーネルレベルの隔離や異なるOS（WindowsやFreeBSDなど）の実行が必要な場合は、KVMを用いた完全仮想マシンを採用します。

一方で、Linuxベースのミドルウェアや開発サーバーをデプロイする場合は、ホストのカーネルを共有するLXCが最適です。LXCはVMと比較してオーバーヘッドが極めて小さく、メモリの消費量も少ないため、限られたリソースのサーバー上に多数の独立した環境を高密度で集約することができます。

### ZFSによるストレージ管理と高可用性

Proxmoxを採用する技術的な利点として、エンタープライズグレードのファイルシステムであるZFSとの強力な統合が挙げられます。ZFSのCopy-on-Write（CoW）特性を活用することで、稼働中のコンテナやVMの完全なスナップショットを数秒で作成できます。

カーネルのアップデート、大規模なライブラリの更新、あるいは破壊的なテストを行う前にスナップショットを取得しておくことで、万が一障害が発生しても瞬時に元の状態へロールバックすることが可能です。また、ZFSのレプリケーション機能を設定することで、複数のProxmoxノード間でデータを非同期に同期し、高可用性（HA）クラスタを構築するための基盤を整えることも容易になります。

### セキュアなネットワーク分離とオーバーレイネットワーク

本番環境と同等のセキュリティとルーティングを再現するためには、ネットワークの論理的な分離が不可欠です。Proxmoxの仮想ネットワークスイッチ機能を利用し、VLANによって開発、ステージング、データベースなどの各セグメントを隔離します。そこにpfSenseやOPNsenseといった仮想ルーターアプライアンスを導入し、厳密なファイアウォールルールとルーティングテーブルを設計します。

さらに、これらのプライベートな開発リソースに対して安全にアクセスするための経路として、WireGuardやTailscaleに基づくオーバーレイネットワークを構築します。これにより、複雑なポートフォワーディングやNAT越えの設定を回避しつつ、外出先からでもエンドツーエンドで暗号化されたシームレスな接続が確立されます。ローカルマシンに負荷をかけることなく、クラウド上のリソースを手元のエディタ（VS CodeのRemote Developmentなど）から直接操作する、現代的で柔軟な開発体験が実現します。

## Proxmox 仮想化環境：運用思想とコンテナ(Docker)との対比

過去の議論において、開発環境およびサーバー構築の基盤として Proxmox VE (Virtual Environment) が言及されています。このドキュメントでは、Proxmoxを利用するメリット、デバイスパススルーの優位性、およびDockerとの明確な違いについて考察します。

### 1. Proxmox VE の本質

Proxmoxは、Debianベースのベアメタルハイパーバイザーであり、KVM（Kernel-based Virtual Machine）を用いた完全仮想化と、LXC（Linux Containers）を用いた軽量なコンテナ型仮想化の両方を一つのWeb UIから統合管理できる強力なプラットフォームです。

#### 1.1 Dockerとの決定的な違い
過去のログにおいて、「ProxmoxはDockerと違ってOSごと仮想化している」と明確に定義されています。
- **Docker**: ホストOS（Linux）のカーネルを共有し、名前空間（Namespace）とCgroupsによってプロセスを隔離する。軽量で起動が速いが、カーネルレベルの変更や異種OSの実行は不可。
- **Proxmox (KVM)**: ゲストOSごとに個別のカーネルをロードし、完全に独立した仮想マシン（VM）を構築する。

### 2. 実運用におけるProxmoxのユースケース

開発チーム内でProxmoxが検討された最大の理由は、**「環境の完全隔離」と「ハードウェアの柔軟な割り当て」** にあります。

#### 2.1 複数バージョンのOS検証
「Ubuntuの違うバージョン試したりできる」
ROS（Robot Operating System）の開発においては、特定のバージョン（例: ROS1 NoeticはUbuntu 20.04、ROS2 HumbleはUbuntu 22.04、Jazzyは24.04）が特定のOSに強く依存します。Proxmoxであれば、1台の強力な物理サーバー上に、異なるバージョンのUbuntu VMを同時に稼働させ、それぞれの環境で独立してCIビルドや動作検証を行うことが可能です。

#### 2.2 USB/PCIe デバイスのパススルー
「デバイスのパススルーのこと考えたら割と使える場面はありそう」
Dockerコンテナにホストのデバイス（`/dev/ttyUSB0` 等）をマウントする場合、パーミッション問題やコンテナ再起動時のデバイス消失といった面倒なトラブルがつきまといます。
ProxmoxのKVM仮想マシンに対してPCIeパススルー（IOMMU）やUSBパススルーを設定すれば、仮想マシン内のOSからはそれが**物理的に直結されているハードウェア**として認識されます。これにより、udevルールやsystemdサービスを用いた通常のLinuxと同等の泥臭いハードウェア制御が、仮想環境上でも完全に再現可能となります。

### 3. 懸念点とパフォーマンスのトレードオフ

#### 3.1 「でも重くないのかな」
完全仮想化であるため、Dockerのようなプロセス隔離と比較すると、CPUのオーバーヘッド、そして何より**メモリの消費量**が大きくなります。
各VMが独自のOSカーネルとバックグラウンドサービス（systemd等）を実行するため、複数台のVMを立ち上げるには物理サーバー側に潤沢なリソース（特にRAM）が要求されます。

#### 3.2 結論と棲み分け
- **Proxmox (VM) を使うべき場面**: カーネルレベルのモジュール（特定のネットワークドライバや特殊な仮想インターフェース）が必要な場合、デバイスのパススルーをネイティブ同様に扱いたい場合、あるいはOSそのものを破壊する可能性があるテスト環境の構築。
- **Docker / LXC を使うべき場面**: 既にベースとなるOS環境が整っており、単純にアプリケーション（Webサーバー、DB、特定のミドルウェア）のみを隔離して軽量かつ大量にデプロイしたい場合。

Proxmox上でLXCコンテナとKVM仮想マシンを用途に応じて使い分け、さらにVMの中でDockerを走らせる（あるいはAnsibleでプロビジョニングする）といった柔軟なハイブリッド構成が、現代のインフラ構築における強力な解となります。
