# CI/CD パイプライン：構築思想、ビルド高速化、泥臭いトラブルシューティング

過去の議論履歴から抽出した、開発における Continuous Integration (CI) および Continuous Deployment (CD) に関する知見、エラー解決手法、およびアーキテクチャの選定基準について高密度にまとめます。

## 1. CI/CDの哲学と Pull Request (PR) 運用

### 1.1 PRは細かく刻み、CIに任せる
「行数が10,000行を越えるような巨大なPRは、不用物（`build/` や `log/`）が混入している可能性が高い」と指摘されているように、PRはなるべく小さな粒度で分割し、マージしていくことが推奨されます。
- **.gitignoreの早期適用**: ビルド生成物や一時ファイルがリポジトリに混入することを防ぐため、プロジェクト初期に `.gitignore` を適切に設定することが必須です。万が一混入した場合は `git rm -r` で削除し、早急にメインブランチにマージしてCIを通す。
- **CIを通すためのPR**: PRの主な目的が「レビュー」から「CIによる自動チェック（ビルドテスト、静的解析など）」にシフトしつつある現状が議論されています。自動化されたチェックを通過してからレビューを行うことで、属人性を排除します。

## 2. GitHub Actions による自動化戦略

### 2.1 セルフホストランナーの活用
大規模なコンパイル（特にC++やRust、OpenCVを含むROS2プロジェクト）は、GitHubが提供する無料のホストランナーでは時間とリソースが圧倒的に不足します。
- `rodep-rescue2026/settings/actions/runners` などに見られるように、研究室や手元の強力なPC（NUC等）を **Self-Hosted Runner** として登録し、余剰なマシンパワーをCIビルドで殴る運用が強力です。

### 2.2 ドキュメントの自動デプロイ (CD)
ドキュメント管理において、生のマニュアル(md)をリポジトリに放置するのではなく、**Sphinx (reStructuredText)** を用いてドキュメントをビルドし、GitHub Actions経由で **GitHub Pages** に自動デプロイするフローが構築されています。
- *「docsはmdで管理するのやめてSphinx(rst)で管理してgithub pagesにactionsからデプロイします」*

## 3. コンパイル/ビルドの泥臭い最適化と罠

CI上で実行されるビルドタスクは、環境によって深刻な遅延やエラーを引き起こします。

### 3.1 ツールチェーンごとの実行時間比較
過去の計測から、以下のビルドツールの重さが比較されています。
- `colcon build`: 比較的軽量（数分程度）。ただし依存関係が複雑だと失敗しやすい。
- `cargo build`: 非常に重い。特にOpenCVなどの外部C++ライブラリをRustクレート経由でビルドする場合、数十分の時間を要する。キャッシュ戦略が必須 (`rust-cache` アクションの導入など)。
- `nix develop`: キャッシュが効いていないと数十分単位で時間が溶ける。

### 3.2 CI上でのDockerコンテナビルド
CI環境内でさらにDockerイメージをビルドしてテストを回す場合、`COPY` コマンドの順番（キャッシュレイヤーの最適化）がビルド時間を大きく左右します。
また、「devshellに書いたパッケージがDocker imageに含まれていない」といった、NixとDockerを併用した際特有の罠も報告されています。

## 4. ネットワークとインフラの自動化 (IaCの萌芽)

インフラ構築の自動化（Infrastructure as Code）の思想が、CI/CDの議論に結びついています。
- **Ansibleの活用**: 「ubuntu入れたらあとはansibleのコマンド一発で一度もNUC触らずにネットワーク完備＆本番ロボット環境deployまでもっていってやる」
- IPアドレスの割り当てにおいて、安易に `dhcpcd` で殴り込むのではなく、現代的な `systemd-networkd` にDHCP管理を任せるべき、といったOSレイヤーのネットワーク設定の自動化・健全化も、継続的デプロイメントの安定性を支える重要な要素です。
