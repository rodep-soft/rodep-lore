# 履歴操作の芸術：安全で美しいコミットグラフの構築

複雑なプロジェクトにおいて、ブランチの合流を無計画に `git merge` で行うと、コミットグラフが網の目のように絡み合い、変更の文脈を追うことが困難になる。履歴を直線的かつ論理的に整理するための高度な手法について解説する。

## Rebaseの真価とインタラクティブ・リベース

自身の作業ブランチを最新のメインブランチに追従させる際には、`git rebase` を活用して履歴を直線的に保つことが推奨される。特に `git rebase -i`（インタラクティブ・リベース）を用いることで、ローカルでの試行錯誤の過程（「WIP」や「typo修正」といったコミット）を統合（squash/fixup）したり、意味のある単位に再構築することが可能だ。

これにより、レビュアーや将来の自分に対して「なぜこの変更を行ったのか」という文脈を明瞭に伝える、ノイズのない美しい履歴を残すことができる。

## 安全な強制プッシュ：--force-with-lease と --force-if-includes

Rebaseによってコミット履歴を書き換えた場合、リモートリポジトリへ反映させるには強制プッシュが必要となる。このとき、単純な `git push --force` を使用すると、他者が追加したコミットを誤って上書きしてしまう危険がある。

現代のGit運用においては、`git push --force-with-lease` を使用することが必須である。さらに、Git 2.30以降では `--force-if-includes` オプションを併用することで、ローカルでフェッチしていないリモートの変更を上書きしてしまう事故をより厳格に防ぐことができる。設定ファイルに `push.useForceIfIncludes = true` を追加しておくことを推奨する。

## 破壊的操作への備えと命綱

作業中に不用意に `git reset --hard` を実行すると、未コミットの変更が失われるリスクがある。コミットをやり直したいが変更内容を保持したい場合は `git reset --soft` を活用すること。

一時的な作業の退避には `git stash push -m "メッセージ"` を用いて意図を記録することが望ましい。万が一、誤った操作で重要なコミットを消失してしまった場合でも、焦る必要はない。`git reflog` を使用することで、過去のHEADの移動履歴をたどり、特定の状態へ確実に戻すことが可能だ。
