# チームの暗黙知を形式知へ：環境のコード化とコミュニケーション

ソフトウェア開発はコードを書く時間以上に、チーム間での意思疎通や環境構築に時間を費やします。プロジェクトの属人化を防ぎ、持続可能な開発体制を築くためのプラクティスについて解説いたします。

## チャットツール依存からの脱却とストック情報の蓄積

バグの報告や仕様変更の議論、環境構築時のトラブルシューティングを、SlackやDiscordといったチャットツールのみで完結させることは避けるべきです。チャットツールは「情報のフロー（流れる情報）」には適していますが、「情報のストック（蓄積される情報）」には不向きです。

重要なアーキテクチャの意思決定（ADR: Architecture Decision Records）や、環境起因のノウハウは、必ずGitHubのIssueやDiscussions、またはドキュメントとして記録してください。これにより、後から参加したメンバーが容易に過去の文脈を検索できる文化が醸成されます。

## 環境差・機体差の分離戦略

ハードウェアが絡むプロジェクトにおいて、機体固有のパラメータ調整などをコードベースに直接書き込むことは、メインブランチの汚染に繋がります。環境や機体に依存する設定は、コード本体から分離し、環境変数（`.env`）や外部のコンフィグレーションファイルとして読み込む設計を採用してください。

これにより、同一のバイナリやコンテナイメージを、異なる環境へ安全にデプロイすることが可能となります。

## エディタ設定とグローバル除外設定の活用

開発者ごとの個人的なエディタ設定（ローカル設定や `.idea/` など）をリポジトリに含めることは避けてください。プロジェクト全体で共有すべきフォーマッターの設定（`.vscode/settings.json` の一部など）のみをコミットし、個人の趣味趣向に依存するファイルは、各開発者の `~/.gitignore_global` などのグローバル除外設定に委ねるのが適切な役割分担です。

さらに、`.gitattributes` ファイルを活用することで、OSごとの改行コードの違い（CRLFとLF）による無用な差分を防ぎ、GitHub上の言語統計を正しく制御するなど、プロジェクトレベルでの細やかな統制が可能となります。
