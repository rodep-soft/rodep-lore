# チーム開発のためのGit・GitHub運用術

本記事では、チーム開発におけるGitの高度な使い方、運用フロー、および開発プラクティスについて解説します。

Gitを単なるバージョン管理ツールとして捉えるのではなく、チーム開発における「コミュニケーションツール」として活用することが重要です。
ここでは、私たちが普段どのような思想でGitを運用しているのか、陥りやすい問題点も含めて紹介します。

## 1. コミットとブランチの運用思想

### 実機で動作するまでコミットしないのは避ける
よくあるアンチパターンとして、「完璧に動作する状態になるまでコミットしない」というものが挙げられますが、これは避けるべきです。
コードが完成していなくても、トピックブランチを作成し、細かくコミットとプッシュを行っていくのが適切な進め方です。
もしビルドが通らない状態であれば、`colconignore`を配置してビルド対象から外すなどの対応が考えられます。
重要なのは、早い段階でGitHub上に反映し、チームメンバーからレビューやフィードバックをもらえる状態を構築することです。

### プルリクエストの長期放置によるコンフリクト
プルリクエスト（PR）を長期間放置すると、メインブランチとの差分が拡大し、コンフリクトの解決が非常に困難になるリスクが高まります。
Draft PRやIssue、Discussionsなどを活用し、現在の作業状況を透明性高く共有しながら進めることを推奨します。

### コミュニケーションツール上の議論をドキュメント化する
バグ報告や、WSL2/Dockerの環境構築におけるつまずき、新しいタスクなどについて、チャットツール（Discordなど）上のやり取りだけで完結させるのは望ましくありません。
後から検索可能にするためにも、必ずリポジトリのIssueやDiscussionsに記録を残すようにしてください。蓄積された知見はチームの重要な資産となります。

## 2. 安全な履歴操作

### 共有リポジトリでの `--hard` オプションのリスク
チーム開発中に不用意に `git reset --hard` を実行すると、未保存の作業データが失われるリスクが伴います。
作業を一時的に退避させたい場合は、`git stash push` を使用するか、コミット履歴を保持できる `git reset --soft` の利用を検討してください。

## 3. サブモジュール（Git Submodule）とリポジトリの分離

### 外部の巨大なコードベースは `git submodule` で管理する
micro-ROSやモータードライバなど、外部で開発されている巨大なコードベースを直接プロジェクトのディレクトリツリーに含めると、リポジトリが肥大化してしまいます。
このような場合は、独立したリポジトリとしてForkし、`git submodule` を用いて管理することが適切です。これにより、リポジトリのクローンにかかる時間も短縮されます。

### 個人設定（ドットファイル）のコミットを避ける
NeovimやVS Codeなどの個人的なエディタ設定（ドットファイル）を、チームの共通リポジトリにコミットしたりSubmoduleとして追加したりすることは避けてください。
プロジェクトのリポジトリには、あくまでチーム全体で共通して使用する開発設定のみを含めるようにします。

## 4. トラブルシューティングとよくある注意点

### `.gitignore` の設定漏れによるバイナリファイルの混入
`a.out`、`main.exe`、または `build/` ディレクトリ内の生成物など、バイナリファイルを誤ってコミットしてしまうと、GitHub上で差分を表示する際にブラウザの動作が重くなるなどの問題が発生します。
誤ってプッシュしてしまった場合は、`git rm --cached` コマンドで追跡を解除し、当該ファイルを `.gitignore` に追記して対応してください。

### Gitが空ディレクトリを追跡しない仕様への対策
Gitの仕様として、空のディレクトリはバージョン管理の追跡対象になりません。
ローカル環境では空ディレクトリが存在するためにビルドが通っていても、GitHub ActionsなどのCI環境で「ディレクトリが存在しない」というエラーが発生することがあります。
これを防ぐためには、空ディレクトリ内に `.gitkeep` ファイルを配置するか、ディレクトリの生成処理をビルドスクリプトに組み込む必要があります。

### 機体や環境ごとのパラメータ管理
複数の機体（例えば1号機や2号機）に依存するパラメータ調整などを直接メインブランチにマージすると、コードの整合性が失われる恐れがあります。
このような場合は、機体ごとにタグを打つか、あるいは専用のブランチを分けて運用することが基本原則となります。
