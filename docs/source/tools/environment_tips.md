# 環境構築の極意 (Docker / WSL2 / Ubuntu / Proxmox)

環境構築は複雑化しやすく、想定外のトラブルに見舞われることも少なくありません。
しかし、いくつかの重要なポイントを押さえておくことで、後々の不具合を大幅に防ぐことができるでしょう。

## 1. Docker / Docker Compose / DevContainer について

### MacやWindowsでDockerを使用する際の留意点
前提として、**Dockerは本来Linuxのカーネル機能（CgroupsやNamespaces）に依存している**という事実があります。
つまり、macOSやWindowsでDockerを動作させる際は、背後でハイパーバイザ上のLinux VMが稼働しています。ネイティブのLinux環境と比較すると、I/Oやコンテナの起動にオーバーヘッドが生じることは避けられません。そのため、これらの環境でDockerの動作が遅く感じられるのは、アーキテクチャ上の仕様と言えます。

### マルチステージビルドによるスリム化
C++やRustのようなコンパイル言語を使用する場合、**マルチステージビルド**は非常に有効な手法です。
ビルド用と実行用のコンテナを分離することで、デプロイ用のイメージからコンパイラやビルド依存のパッケージを排除できます。結果としてイメージサイズを劇的に軽量化できるため、積極的に導入することをお勧めします。

### チーム開発におけるDevContainerの活用
開発者によって「自分の環境では動作するが、他の環境では動かない」といった問題が発生することは珍しくありません。
こうした事態を防ぐためにも、VS Codeの**DevContainer (`.devcontainer`)** の導入が推奨されます。これを設定することで、チーム全体で開発環境、ツールチェーン、コンテナの設定を完全に統一できます。環境構築に起因する不要なトラブルを減らすことができるでしょう。

## 2. WSL2 (Windows Subsystem for Linux 2) の活用

### USBデバイスのパススルー (`usbipd-win`)
WSL2を使用していると、ST-LinkやCANアナライザ、LiDARなどのUSBデバイスが認識されないという問題に直面することがあります。
そのような場合は、**`usbipd-win`** を活用すると良いでしょう。
PowerShell側で `usbipd bind` を実行し、WSL2起動時に自動でアタッチされるようスクリプトを組んでおくことで、開発効率を大きく向上させることができます。

### WSL2カスタムカーネルビルドの推奨
WSL2の標準カーネルでは、`joydev`（ジョイスティック `/dev/input/js*`）や仮想CANなどが無効化されています。ロボティクス分野の開発においては、これが障害となる場合があります。
この問題への対策として、Microsoftが公開しているWSL2用のLinuxカーネルソースを取得し、カスタムビルドを行う方法が効果的です。
`make menuconfig` で `CONFIG_INPUT_JOYDEV=y` などを有効にしてビルドし、そのカーネルを `.wslconfig` で指定して起動します。一見すると難易度が高く感じるかもしれませんが、手順を踏めばスムーズに実現できるため、ぜひ試してみてください。
