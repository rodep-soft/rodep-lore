# micro-ROS

STM32などのマイコン上でROS2のエコシステムを動かすmicro-ROSと、`ros2_control`を使ったハードウェア制御の実装記録。実際にハマった箇所を中心にまとめている。

### 1. micro-ROSの導入とパフォーマンスの葛藤

組み込み環境において、ROS2のエコシステムをそのまま利用できるmicro-ROSは非常に魅力的です。CubeMXを用いてプロジェクトを初期化し、`micro_ros_stm32cubemx_utils`を組み込むことで、STM32上でROS2ノードをネイティブに動作させることが可能です。

しかし、実際のパフォーマンスを追求すると、フレームワークのオーバーヘッドが無視できなくなります。特に、エンコーダの読み取りやPWM制御において、STM32のHAL（Hardware Abstraction Layer）を使用するのではなく、LL（Low-Layer）APIを用いた方がレジスタへの直接アクセスが可能となり、劇的なパフォーマンスの向上が見込めます。

このため、「単純にシリアル通信やDMA、タイマーを直接制御し、PC側のPythonスクリプトやC++ノードでROS2ネットワークへブリッジした方が実用的ではないか」という議論が絶えません。micro-ROSはあくまで高レベルの抽象化を提供するものであり、数ミリ秒単位の厳密なリアルタイム性が要求されるレイヤーにおいては、ネイティブ実装への回帰が検討されるべきです。

#### サブモジュール管理とビルドの苦悩

micro-ROSをプロジェクトに組み込む際、Gitのサブモジュール管理が非常に煩雑になります。また、Docker Composeを用いてビルド環境をコンテナ化した場合、依存関係の解決とクロスコンパイルのプロセスによってビルド時間が著しく増大します。解決策として、micro-ROSのコア部分をフォークし、必要な機能のみを静的にリンクする手法や、ビルド済みバイナリをキャッシュする仕組みの導入が不可欠です。

### 2. ros2_controlとMoveIt2の統合

ロボットアームなどの多関節ロボットを制御する際、`ros2_control`と`MoveIt2`の連携が標準的なアプローチとなります。しかし、これらのフレームワークはパラメータが非常に多く、設定ファイル（YAML）の記述ミスが致命的なエラーを引き起こします。

#### ジョイント軌道の確認とトラブルシューティング

MoveIt2が生成した軌道（Trajectory）が正しくコントローラに送信されているかを確認するためには、以下のコマンドを使用します。

```bash
ros2 topic echo /sekirei_arm_controller/joint_trajectory_controller/commands --once
```

しかし、システム立ち上げ初期には、このコマンドを実行してもデータが一切出力されない（プロンプトが戻ってこない）問題が頻発します。この原因の多くは、コントローラが適切にロードされていない、あるいはアクティブ化されていないことに起因します。以下のコマンドでパラメータの状態を確認した際の失敗例です。

```bash
root@tatsv:~/ros_ws# ros2 param get /servo_node controller_name
Parameter not set
```

パラメータが正しく設定されていないため、サーボノードがコマンドを受け付けない状態に陥っています。

#### Fake Controllerの実装

`ros2_control`のハードウェアインターフェースをゼロから実装するのは学習コストが極めて高いため、初期段階ではMoveIt2が生成した軌道を受け取り、そのまま`JointState`として送り返す（実機を動かさずにRViz上だけで動作を確認する）Fake Controllerのアプローチが有効です。

その後、実機を接続し、MoveIt Servoを用いてリアルタイムな制御を行う場合、以下のようにコマンドタイプを切り替えるサービスコールが必要になります。

```bash
ros2 service call /servo_node/switch_command_type moveit_msgs/srv/ServoCommandType "{command_type: 0}"
```

### 3. センサーフュージョンと自己位置推定

移動ロボットの制御において、エンコーダ（オドメトリ）とIMU（BNO055等）の融合は必須です。しかし、エンコーダからの`linear.x`のみに頼る推定はスリップ等の影響を強く受けます。

実践的には、IMUからの角速度（angular）と、傾斜を補正するためのロール・ピッチ（orientation）をカルマンフィルタ等でフュージョンするアプローチが取られます。ただし、IMUはドリフトの問題を抱えているため、`imu_filter_madgwick`のようなフィルタリングノードを噛ませることで、ノイズを除去し、より現実的で精度の高い姿勢推定（Odometry）を実現することが重要です。

最終的には、LiDARとIMUを組み合わせたLIO（LiDAR Inertial Odometry）である`KISS-ICP`などのアルゴリズムへ移行し、エンコーダの共分散を大きめに設定（信頼度を下げる）することで、よりロバストな自己位置推定システムを構築することが理想とされます。

## ROS 2におけるZenohとmicro-ROSの統合およびトランスポート層の評価

ROS 2の最新動向において、Zenohの統合はネットワークトポロジーの管理に革新をもたらしています。Zenohのインテグレーションでは、各コンテキストが単一のZenohセッションにマッピングされ、これがコンテキスト内のすべてのパブリッシャー、サブスクリプション、サービス、クライアントで共有される設計となっています。コンテキストはローカルのグラフキャッシュを保持し、ROS 2エンティティのネットワークトポロジーを追跡します。各エンティティの存在は、作成時に発行され破棄時に取り消される一意の「liveliness token（生存トークン）」を通じて管理されます。

組み込み用途では、micro-ROSのトランスポート層としてZenohを採用するアプローチが検討されています。ただし、標準のDDS実装と比較すると、実装の成熟度や対応バージョンにおいて確認が必要です。また、シビアなハードウェア制約がある環境では、単にmicro-ROSを利用するだけでなく、STM32等のマイコンにおいてHAL（Hardware Abstraction Layer）からLL（Low-Layer）APIへ移行し、DMAやハードウェアタイマーを直接制御することでパフォーマンスを向上させるという、より低レイヤーでの最適化が重要となる場面も多々あります。
