# ROS2 のデバッグ・実装手法・システムアーキテクチャ

本稿では、ROS2におけるデバッグや実装手法、およびシステムアーキテクチャに関する重要な知見を共有します。これらの知識の有無は開発速度に直結するため、しっかりと押さえておくことが重要です。

## (1) ノード設計・プロセス内通信・コンポーネント化

### ノード分割のトレードオフ
ノード設計において、機能ごとに細かく分割するとシステムの耐障害性は向上します。しかし一方で、過度に細分化するとDDS通信のオーバーヘッドが増大してしまいます。このバランスを適切に保つことが重要となります。

### プロセス内通信（Intra-process Communication / Zero-Copy）と Component
大容量の画像データを扱う場合や、高頻度な制御においてゼロコピー転送を行いたい場面があります。そのような場合は、`rclcpp::NodeOptions().use_intra_process_comms(true)` を有効にし、メッセージを `std::unique_ptr` で publish/subscribe する必要があります。
これを実現するためには、ノードを共有ライブラリ（Component）としてビルドし、単一のプロセスに動的ロードする構成をとります。一見すると複雑に見えるかもしれませんが、パフォーマンスの観点から非常に有用な手法です。

### `twist_mux` による速度指令の安全統合
手動操作（Joystick）と自動航行（Nav2）のように、複数の速度指令が競合することは珍しくありません。このような時、独自に `switch` 文などで制御を実装したくなりますが、それはアンチパターンとされています。標準の **`twist_mux`** を導入し、優先度とタイムアウトを用いて安全に統合することが推奨されます。

## (2) デバッグ・シミュレーション・トピックの作法

### `use_sim_time:=true` の罠
Gazeboなどのシミュレーション環境やROS Bagの再生時に、ノードへの `use_sim_time:=true` の渡し忘れには注意が必要です。これを忘れると、TF（座標変換）やMoveIt2、Nav2などが一切動作しなくなってしまいます。実機で動かす際は `false` で問題ありませんが、シミュレーション時には確実に設定するようにしてください。

### シミュレーションと実機の透過的切替
トピックの仕様を共通化した仮想コントロールパネルのようなものを用意しておくと、コードを一切変更することなく、シミュレーションと実機をシームレスに切り替えてテストできるようになります。これは開発効率を大きく向上させるため、導入を検討すべき手法の一つです。

### `robot_localization` (EKF / Dual EKF)
IMUや車輪エンコーダなどのセンサ情報の統合には、`robot_localization` を利用するのが一般的です。自己位置推定の際には、ローカル用EKF（`odom` -> `base_link`）とグローバル用EKF（`map` -> `odom`）を組み合わせる **Dual EKF** 構成がデファクトスタンダードとなっています。

### 標準メッセージ規格の尊重
トピックの設計において、独自の構造体をむやみに作成することは避けるべきです。基本的には `std_msgs`、`sensor_msgs`、`geometry_msgs` といった標準のメッセージ型を優先して使用します。
CAN通信においても、各ドライバで独自のものを定義するのではなく、ROS2標準規格である **`can_msgs/msg/Frame`** に依存してノードを作成することが、今後の相互運用性を考慮すると極めて重要になります。
