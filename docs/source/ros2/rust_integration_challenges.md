# ROS2とRustの統合に関する課題

ROS2のノードをRustで記述する（`ros2_rust` / `rclrs`）際のアーキテクチャ上の課題と、ビルドプロセスにおける問題点について整理します。

## 依存関係とバージョン不整合

`rclrs`と`sensor_msgs`などの標準メッセージパッケージとの間で、要求されるバージョンが一致せずにビルドが進行できなくなるケースがあります。ROS2のディストリビューション（HumbleからJazzyなど）の移行期においては、内部で使用されるPythonのバージョン（3.10から3.12への変更）に伴う破壊的変更の影響も受けやすく、依存関係の解決にはC++以上に慎重なバージョン指定が求められます。

## スレッドセーフティと設計思想の乖離

公式のサンプルコードでは簡素に書かれていますが、実際のドライバやサブスクライバコールバックをRustで実装しようとすると、複数の構造体間でデータを共有するために`Arc<Mutex<T>>`を多用せざるを得ない場面に直面します。これはRustの安全性を担保する一方で、ROSの本来の軽量なPub/Subモデルの思想からすると冗長であり、C++での単純なポインタ渡しやコールバックと比べて実装が複雑になりがちです。

## ビルド時間の増大

`colcon build`から内部で`cargo build`が呼び出される構成をとった場合、依存するC++ライブラリ（例えばOpenCVのRustラッパーなど）のコンパイルが挟まると、非常に長いビルド時間が発生します。開発サイクルを回す上では、ROSの通信部分のラッパーと純粋なRustライブラリ部分を分離し、Rust側のロジック単体でテストやビルドを行えるようにする設計が推奨されます。
