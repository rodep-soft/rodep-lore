# プログラミング知見・設計思想まとめ

お疲れ様です！今回は、C++やPython、Rustといった言語ごとのハマりどころから、僕たちが大切にしている設計思想まで、チームで溜まってきた知見をシェアしたいと思います。
単なる仕様の話ではなく、「実戦でどう使うか」にフォーカスしていくので、ぜひ今後の開発に活かしてくださいね！

## 1. C++ のハマりどころと最適化

まずは我らが C++ です。強力な言語ですが、油断すると痛い目を見ますよね（笑）。

**型選定と `size_t` の扱い**
`std::vector::size()` の戻り値と比較するとき、とりあえず `size_t` を使っていますよね？でも、`size_t` って環境依存の「符号なし整数（unsigned）」なんです。これを普通の `for` ループのカウンターで逆ループとかに安易に使うと、あっという間にアンダーフローして謎のバグを引き起こしちゃうんですよね。気をつけていきましょう！

**`volatile` の誤用と排他制御**
これ、意外と勘違いしがちなんですが、`volatile` はあくまで「コンパイラの最適化（レジスタキャッシュ）を抑制して、ハードウェアアクセスを保証する」ためのものなんです。C++の仕様上、マルチスレッド間のスレッドセーフ（排他制御）を保証するもの**ではない**というわけです。マルチスレッドでの同期が必要なら、ちゃんと `std::atomic` や `std::mutex` を使ってくださいね。

**スマートポインタとコールバックの寿命**
ROS2 でノード内のコールバックやタイマーで `this` をキャプチャするシーン、よくありますよね。このとき、コールバックがノードオブジェクトより長生きしてしまうと、循環参照やクラッシュの原因になります。こういう時は迷わず `weak_from_this()` や `std::weak_ptr` を使いましょう！

**テンプレートの使いすぎに注意**
C++の醍醐味である `template` ですが、小さな処理にまで安易に多用すると、コンパイル時間が爆発してコードも肥大化しちゃいます（笑）。ビルドが遅いと感じたら、高速リンカーの **`mold`** を導入するのもめちゃくちゃ効果的ですよ！

**静的解析で品質を担保しよう**
メモリリークや未定義動作は、人間が見つけるのは限界があります。だからこそ、`AddressSanitizer` や `UndefinedBehaviorSanitizer` といった `sanitizer`群、そして `perf` や `clang-tidy` をビルドパイプラインに組み込んで、機械的に早期発見できる仕組みを作っていきましょう。

## 2. Python の使いどころと限界

Pythonは最高に便利ですが、適材適所が大事だと思っています。

**どこで使うべきか？**
複雑なオブジェクト指向（OOP）をガチガチに組むような大規模システムには正直向いていません。でも、データ解析や CLI ツール（`subprocess`でサクッと）、通信プロトコルのプロトタイプ作成（`requests`とか）、テストの自動化なんかでは、圧倒的な威力を発揮しますよね。適材適所で使い倒しましょう！

**GILの壁とパフォーマンス**
Pythonには「GIL (Global Interpreter Lock)」という大きな制約があります。これと動的型のオーバーヘッドのせいで、プロセス内ゼロコピーや数kHzオーダーの超低レイテンシな制御・通信には全く適していません。高頻度な処理は無理せず C++ や Rust に任せるという割り切りが大事です。

## 3. Rust のハマりどころと強力な機能

最近勢いのある Rust ですが、これも学習曲線がエグいですよね（笑）。

**所有権と Borrow Checker との戦い**
双方向リストとかグラフ構造を Rust で素直に書こうとすると、Borrow Checker にボコボコにされます（笑）。結果的に `Option<Rc<RefCell<Node>>>` みたいなネストの「型地獄」に陥りがちです。
あと、本番コードでの `unwrap()` の多用は絶対にやめましょう！面倒でも `?` 演算子や `match`、`if let` を使って徹底的にエラーハンドリングするのが Rust の流儀です。

**`clap` が最高すぎる**
CLI を作るなら `clap` パッケージの `derive` スタイル一択と言っても過言じゃないです。非常に型安全かつ宣言的にコマンドライン引数をパースできるので、もうこれなしでは CLI は書けない体になっちゃいますよ。

**パフォーマンスは C++ 級**
Rust の `--release` ビルドの最適化は本当に優秀で、C++ の `-O3` ビルドと同等かそれ以上の速度を叩き出すことも多いです。パフォーマンスと安全性が両立できるのはデカいですよね。

## 4. ソフトウェア設計の「思想」

最後に、コードを書く上での「心構え」についても共有しておきます。

**コピペエンジニアにならないために**
最近は AI も便利だし、ネットにもコードが溢れてます。でも、内部構造や動作要件を理解せずにコードを組み込む「カーゴ・カルト・プログラミング」は絶対に警戒してください。それと、デザインパターンを適用すること自体が目的になってしまう（Pattern Zealot）のも本末転倒です。「課題解決」が一番の目的だということを忘れないでくださいね。

**早すぎる最適化は諸悪の根源**
「Premature optimization is the root of all evil」という有名な言葉がありますよね。最初から完璧なパフォーマンスを求めてコードを複雑にするのは悪手です。まずは「シンプルに動くコード」を書き、計測してボトルネックが判明してから最適化する、という順序を守りましょう。

**「神オブジェクト」を作らない**
1つのノードやクラス（たとえば `joy_controller` とか）の中に、キネマティクス計算から状態遷移、通信処理まで全部詰め込むのは典型的なアンチパターンです。いわゆる「God Object」ですね。これをやると後から誰もメンテできなくなります（笑）。「単一責任の原則」を意識して、コンポーネントは適切に分割していきましょう！
