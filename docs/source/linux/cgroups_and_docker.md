# Cgroups And Docker

## Dockerの内部構造とLinuxカーネルの機能

コンテナ技術を支える基盤技術であるNamespaceとCgroup、そしてDocker Engineの変遷について解説します。

### NamespaceとCgroup

コンテナは仮想マシンとは異なり、ホストOSのカーネルを共有します。Dockerデーモン（`dockerd`）は、Linuxカーネルの機能である「Namespace」を利用してプロセス、ネットワーク、マウントポイントなどを隔離し、「Cgroup」を利用してCPUやメモリのリソース制限を適用します。これにより、コンテナ内のプロセスからは独立したOSのように見えます。

### Dockerアーキテクチャの変遷

初期のDockerは巨大な単一のデーモンがすべてを管理していましたが、現在ではモジュール化が進行しています。具体的には、`dockerd`がリクエストを受け取り、`containerd`（コンテナのライフサイクル管理）に処理を委譲し、最終的に`runc`という低レベルランタイムがNamespaceやCgroupの設定を行ってプロセスを起動します。この仕組みにより、KubernetesなどもDockerに依存せず、直接`containerd`を利用する構成が標準化されました。

### ネットワークとセキュリティ

コンテナのネットワーク設定において、`network_mode: host`や`privileged: true`を安易に指定することは、ホストのネットワーク名前空間やリソースへの無制限なアクセスを許可することと同義であり、セキュリティ上の大きなリスクを伴います。例えば、コンテナ内に不正侵入された場合、ホストネットワーク上の他のデバイスに対してARPスプーフィングなどの中間者攻撃が容易に行われる危険性があります。Linuxにおいてネットワークインターフェースの設定を変更するには`CAP_NET_ADMIN`権限が必要であるという基本原則を理解しておくことが重要です。

## DockerのLinuxカーネル依存性とcgroupsの役割

Dockerコンテナは、仮想マシン（VM）とは異なり、ホストマシンのカーネルを共有する技術です。この仕組みの根幹には、Linuxカーネルが提供する「cgroups（コントロールグループ）」や「名前空間（Namespaces）」といったリソース隔離機能が存在します。

そのため、Dockerは本質的にLinux環境を前提としており、macOSやWindows上でDockerをネイティブに動作させることはできません。Windows（WSL2経由）やmacOS（Docker Desktopなど）でDockerを利用する場合、背後ではハイパーバイザ（Hyper-Vなど）上で軽量なLinuxカーネルが稼働しており、その上でコンテナが実行されています。

このようなアーキテクチャの違いを理解することは重要です。例えば、Windows環境においてコンテナからのホストネットワークへのアクセスやハードウェア（USBデバイスなど）へのマウントを行う際、Linuxネイティブ環境とは異なる制約やオーバーヘッドが発生します。安定したROS 2やロボット制御システムの開発においては、可能な限りネイティブなLinux環境を使用することが推奨されます。

## cgroupsによるリソース分離とリアルタイム性確保

ロボットシステム上では、画像処理、経路計画、センサー制御など、計算負荷や要求されるリアルタイム性が異なる多数のプロセスが同時に稼働します。これらが限られたCPUやメモリリソースを奪い合い、ミッションクリティカルな処理が遅延する事態は避ける必要があります。このような場面で不可欠となるのが、`cgroups`（Control Groups）による厳格なリソース分離です。

現代のLinuxでは、階層構造が統合された `cgroups v2` が主流となっています。これにより、システム内の特定のサービスやプロセスグループに対して、CPU使用時間（`cpu.max`）やメモリ使用量の上限を設けることが容易になりました。特にメモリ管理においては、ハードリミットである `memory.max` だけでなく、スワップやページキャッシュの回収を促すソフトリミットの `memory.high` を適切に設定することで、システム全体のOOM（Out Of Memory）によるパニックを未然に防ぐことが可能です。

メモリ枯渇時にシステムを守るOOM Killerの挙動制御も重要です。例えば、モータ制御ノードなど絶対に停止してはならないプロセスに対しては、`/proc/<pid>/oom_score_adj` に負の値を設定し、キル対象から除外する措置が求められます。
さらに、厳密なタイミングが要求される処理には、カーネルの `PREEMPT_RT` パッチの導入を検討するとともに、`chrt` コマンドを使用してスケジューリングポリシーを `SCHED_FIFO` や `SCHED_RR` へ変更し、CPUコアを占有させる `isolcpus` や `taskset` と組み合わせることで、確実な実行レイテンシを担保するチューニングが実践されます。
