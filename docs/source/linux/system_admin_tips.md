## 1. ファイルシステムとLinuxの本質ってやつ
まず最初にお伝えしたいのが、**Inodeの本質**です。
これ、マジで重要なんですよね。Inodeってデータそのものじゃなくて、ディスク上のブロックを指す「ポインタ構造体」なんです。だから、ファイルの本質って実は「名前や拡張子」にはないんですよ！Windowsとかだと拡張子で判断しがちですが、Linuxでは拡張子なんてただの飾り（文字列）に過ぎないんです。実行できるかどうかはパーミッションとかマジックバイトで決まるっていうわけです。この感覚、絶対持っておいてくださいね！ちなみに、空ディレクトリをまとめて消すときは `rmdir -p` が便利なのでオススメです。

あと、Arch LinuxやUbuntuを使ってるみんな、**「庭師」的なメンテナンス**、ちゃんとやってますか？
`yay`とか`docker`、`pacman`をゴリゴリ回してると、ビルドキャッシュとかで1TBのSSDなんてあっという間にパンパンになります（笑）。ビルドキャッシュが178GBになったこともありましたからね…。定期的に `docker system df` とか `pacman -Scc` を叩いて、雑草を刈り取るようにシステムを綺麗に保つのがプロの嗜みってもんです！

## 2. ログ調査とプロセスデバッグの極意
トラブったとき、どうやってログ見てます？
大量のログを見るときは、やっぱり `less` と `journalctl` がLinuxの王道ですよね！UbuntuやArchだとシステムサービスのログは全部 `journalctl` に集約されてるんで、問題が起きたらとりあえず `journalctl -u gdm.service` みたいにサービス指定でログを叩く！これが問題解決の第一歩だと思っています。

それから、カーネルやプロセスの状態を見たいときは `/proc` や `/sys` の構造を知っておくのが超大事です。例えば `/proc/<pid>/stack` を見れば、プロセスが `futex_wait` で固まってるな〜とか一発で分かりますからね。システムコールの解析には `strace` を組み合わせていくスタイルが最強です。

プロセスの裏側実行は `nohup command &` が手軽で安定してますが、実運用なら `tmux` や `systemd` へのサービス化を使い分けられるようになるとカッコいいですよね。
あ、そうだ！ROSノードが暴走して止まらなくなったときの必殺技教えますね。
`pkill -9 -f ros && ros2 daemon stop`
これでバックグラウンドのデーモンもノードも完全に沈黙させられます。マジで確実なので覚えておいて損はないですよ（笑）。

## 3. ネットワーク運用とDNSの落とし穴
ネットワーク周りってハマると本当に時間溶けますよね…。
よくあるのが `nslookup` と `systemd-resolved` の挙動の違い。`systemd-resolved` 環境下だと、`nslookup` や `/etc/resolv.conf` ってローカルループバック（127.0.0.53とか）を向いちゃってるんですよ。だから実際にどこを参照してるか知りたいときは、迷わず **`resolvctl status`** を叩いてください！これが正解です。

あと、FirewallとかNATの話になると `iptables` とか `nftables` をいじると思うんですけど、あれって実はただの設定インターフェース（フロントエンド）に過ぎなくて、本体はカーネルモジュールの **`netfilter`** なんですよね。こういう本質を知っておくとデバッグの解像度がグッと上がります！ネットワークデバッグで `traceroute` するとき、ICMPやTCPパケットを飛ばしたいなら `sudo traceroute -T <target>` みたいに特権が必要なのも地味なトラップなので注意してください。

TailscaleとかメッシュVPNを使ってる人向けの注意点としては、ローカルの `/etc/hosts` に古い情報が残ってると、MagicDNSよりそっちが優先されて「全然繋がらないじゃん！」ってなる事故がよくあります（笑）。キーの期限切れ（expire）も定期的にチェックして更新する癖をつけましょう！

## 4. シェルスクリプトの罠とPythonへの移行
最後にシェルスクリプトの話なんですけど、みんなFishシェル好きですよね？でも、Fishでスクリプト書いちゃうと、BashとかZshの環境と全然互換性がなくて、自動化のときにマジでトラブルの元になります…。
僕からのアドバイスなんですが、**数行を超えるような複雑な自動化スクリプトは、無理にシェルで書かずにPythonの `subprocess` や `os` モジュールで書く！** これが圧倒的に保守性も移植性も高くてオススメです。

あと、プログラムやってる人がよく陥る罠が「終了ステータス（Exit Code）」の解釈です。
Unix/Linuxコマンドって、終了コード `0` が「成功」なんですよ。これ、プログラムの `True=1`, `False=0` と真逆ですよね？シェルと連携させるときにここで頭バグって条件分岐ミスることめっちゃあるんで、本当に気をつけてくださいね！
