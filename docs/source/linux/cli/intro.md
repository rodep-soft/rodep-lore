# CLI (Command Line Interface)

## CLIとは？
キーボードから文字を入力して操作するインターフェース。GUI（グラフィカルユーザーインターフェース）の対の概念です。日本ではよく*CUI*と呼ばれますが、英語圏や技術界隈では専らCLIと呼ばれます。

情報系の学校などではUnix Comand-Line、所謂「コマンド」を何処かのタイミングで学ぶことが多いでしょう。`ls`, `cd`, `pwd`…といったアレです。苦戦している人も一定数いると思います。

しかし、コマンドを使うと何が良いのでしょうか？格好良いからでしょうか? その意図を多少明確にして、CLIを学ぶモチベーションを高めて貰えれば嬉しいです。

## コマンドは「関数呼び出し」
そもそも私が思うに、コマンドとは自然言語の曖昧さを排除し、機械に確実に伝えるための命令形式です。ある種の人間向けAPIと言えるということで、本質的には関数呼び出しに近いと思っています。

```bash
$ ls -l /home
```

これで「homeディレクトリ以下のファイルまたディレクトリを詳細表示しろ」と命令することができます。それを機械用のフォーマットにしたものというだけですね。

コマンドの書式は大抵、以下のような構造になっています。
```
[何をするか] + [オプション] + [対象]
```
先程の例だと、`ls`でディレクトリの中身を表示、`-l`で詳細表示、その対象が`/home`といった具合です。

## コマンドの正体はただのプログラム
こいつが何処から来てるのか気になる人がいるかもしれませんが、実は大抵のコマンドはただのプログラム名です。C言語をコンパイルするときに、`gcc main.c -o hello`とかすると、`hello`という実行可能ファイルが生成されるわけですが、その`hello`がプログラム名です。

それらが有名どころだと `/usr/bin` や `/usr/sbin` に並べて置いてあり、例えば `ls` は `/usr/bin/ls` と打つのが長いので、デフォルトで `PATH` 環境変数(コマンド探索の検索パス)に `/usr/bin` を追加してあり、プログラム名だけ打てばそれが実行されるという仕組みです。本質的にはみなさんが `./a.out` としてプログラム実行していることと変わらないわけです。コマンド名とは、抽象化された実行名と言えるかもしれません。

シェル由来のものもあるのですべてが元々C(や最近だとRustやGo)のプログラムだったわけではないのですが、基本的にはただのプログラムの寄せ集めです。しかし、非常に強力で70年代から今まで広く使われています。

## Unix哲学とパイプライン
Unixの思想として、「一つのプログラムは一つのことだけをうまくやる」というものがあります。そして、その小さな部品を「つなげて」大きな物を作ったり、複雑なことをするわけです。CLIも勿論例外ではなく、一つのコマンドは基本的に一つのことをうまくやり、それらをパイプラインでつなげて複雑な処理を簡単に行うのです。それぞれのプログラムは疎結合になっています。

パイプラインは「プロセス間通信を標準化したストリーム処理」というと難しすぎるのですが、**関数合成**のようなイメージを持ってほしいです。
`A | B | C` とは意味的には `C(B(A(x)))` と等価です。

多少複雑な例として、例えば簡単なログ解析として、ログファイルの中からエラーを集計して多い順に並べて出力する時、コマンドなら以下です。
```bash
$ cat server.log | grep ERROR | awk '{print $2}' | sort | uniq -c | sort -nr
```
これをGUIでやろうとするとどうでしょうか？想像したくないですね。

ここでポイントなのは、この特定のオペレーションを行うためのコマンドがあるわけではないということです。一つで沢山のことをするコマンドは柔軟性や再利用性を損ないます。これは普段コードを書くときもそうですが、小さいものを組み合わせてプログラムを作る、そして基本的に一つのプログラムは一つの目的だけをうまくやるようにするべきです。関数を小さく分けてコードを書くというのはそういうことです。

## 手続きの再現性と自動化
また、再現性が高いのも強みです。同じコマンドを実行すれば、基本的に同じ結果になります。つまり、「理想的には」決定論的なシステムになっていると言えます。それ故、手順がそのまま記録になり、その手順をシェルスクリプト(`.sh`)としてスクリプト化して自動化することもできます。

例えばとあるweb serverをインストールして立ち上げる時、広く用いられているDebian系Linux(Ubuntuもそう)なら
```bash
$ apt install nginx
$ systemctl start nginx
```
ですが、GUIだとどうでしょうか？
人間の記憶に依存する操作体系が故に再現性が低いです。

CLIであれば、この「手順」が何百行になったところで、
```bash
#!/usr/bin/env bash
apt..
commands…
```
と`.sh`の中で並べてしまえば自動化できますし、この中でループを回したり条件分岐をいれることだってできます。このように、GUIと違い、操作ではなく手続き的なアプローチを取るインターフェースが故の強みがあります。

## その他のメリットまとめ
CLIには、上記で触れた以外にも様々なメリットがあります。

1. **速い、軽い**
   最初は直感的ではないものの、マウス移動やクリックがいらない。GUIにリソースを割かないので実行が速い。
2. **リモート環境に強い**
   GUIでリモートサーバにつなぐのは非効率的だし、サーバは大抵CLI前提。SSH一本で戦える。
3. **PC操作の本質が見える**
   ファイルやプロセス、ネットワーク、権限、OS操作の正体を隠さない。GUIはただの皮。
4. **環境を選ばない**
   Linux, macOS, WSL2, サーバ、コンテナ、どこでも基本同じコマンドが使える。覚えたことが腐らない。
5. **エンジニアの共通語である**
   基本的なCLIコマンドを覚えておくと話が速い。

## おわりに
本当はもっとテキストが接続性に優れたデータ表現である所以や、モジュール化の本質的な部分や現代での進化系などなどについて書きたかったんですが初心者には難しいと判断して辞めます。コマンドラインについては、実際のところ普段から積極的に使ってみることでありがたみを少しずつ実感していくものだとは思います。

> **概念的な理解は後回しで良い**
> まずは脳をCLIに順応させていくことだと思っているので、普段から実機でLinuxを積極的に触ることが近道だと考えています。無い場合はmacOS/WSL2でも良いかもしれません。最初は、基本的な30-50個くらいのコマンドを意識的に使うようにして日常作業ができる程度を目指しましょう。
