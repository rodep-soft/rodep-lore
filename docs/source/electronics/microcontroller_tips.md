# 6. 電子工作・マイコン制御・通信プロトコル (STM32 / CAN / IMU)

お疲れ様です！今回は電子工作やマイコン制御、そして通信プロトコル周辺の知見をガッツリまとめておきますね。STM32とかCAN通信、IMUまわりって、ハマると本当に抜け出せなくなっちゃうことが多いんですよね。だからこそ、ここでしっかり押さえておきたいと思っています！

## (1) STM32 開発とビルド・書き込み環境

### STM32CubeMX + VS Code / Makefile 運用
みんなSTM32CubeIDEを丸ごと使いたくなる気持ちはわかるんですが、実はSTM32CubeMXでペリフェラルやクロックの設定だけをして、MakefileやCMakeとして出力する方が圧倒的におすすめです！その上でVS CodeやPlatformIOで開発するスタイルの方が、後々の拡張性が全然違ってくるんですよね。IDEの独自仕様に縛られないって最高です笑。

### Linux 用 udev ルール設定 (`ST-Link`)
Linux環境でST-Link（Nucleoボードとか）を繋いだとき、「あれ、毎回 `sudo` つけないと書き込めないじゃん…」ってなったことありませんか？これ、`/etc/udev/rules.d/` にパーミッション設定のルールを追加してあげるだけで解決するんです。地味だけど、開発ストレスを減らすために絶対にやっておきたい設定というわけです。

### 非ブロッキングタイマー処理
マイコン制御を始めたばかりの頃って、つい `delay()` を使っちゃいますよね。でも、これを使うと割り込みや他の処理が全部止まっちゃう（ブロッキングされる）ので要注意です！代わりに `HAL_GetTick()` を使って、
`if (HAL_GetTick() - prev_tick >= 1000)`
みたいな感じで、非ブロッキングに周期処理を書くのがプロの作法だと思っています。

## (2) CAN 通信 (Controller Area Network) & SocketCAN

### Physical / Protocol 特性
CAN通信の論理駆動って、Recessive（1）とDominant（0）って言われますけど、これ実はI2Cのオープンドレイン回路と概念的にすごく似ているんですよね。このあたりの物理的なイメージを持っておくと、トラブルシューティングの時にかなり役立ちますよ！

### SPI to CAN (MCP2515) と内蔵 CAN コントローラ
もちろんマイコン内蔵のCANコントローラを使うのが一番低レイテンシで最強なんですが、SPI接続のCANコントローラ（MCP2515とか）も現場ではよく使われますよね。ここで一つ注意！MCP2515を使う時、クリスタル発振周波数（8MHzなのか16MHzなのか）の設定をミスって初期化エラーになる事故が本当に多発しています。動かない時はまずここを疑ってみてください笑。

### Linux SocketCAN とブリッジ
USB-CANアナライザなんかをLinux上で扱う時は、`ros2socketcan` などを噛ませてLinuxの `can0` インターフェースと連携させるのが王道です。これをしておくと、Linux標準のツール（`candump` とか）を使って直接パケット解析ができるようになるので、デバッグ効率が爆上がりするというわけです！

## (3) センサー制御・信号処理 (IMU / フィルタリング)

### I2C クロックストレッチと応答確認
IMUセンサとかでI2C通信がどうも不安定になること、ありますよね。そういう時は、いきなりレジスタアクセスするんじゃなくて、まずは `HAL_I2C_IsDeviceReady()` を使ってデバイスが本当に準備できているか確認するクセをつけましょう。これだけで謎のエラーが激減すると思っています。

### IMU ドリフトと 1次ローパスフィルタ (IIR)
最後にIMUのドリフト対策について。角速度を単純に積分するだけだとバイアス誤差がどんどん溜まっていくので、静的なキャリブレーションだけでは全然防げないんですよね。
標準的なアプローチとしては、まずFFTでノイズの周波数帯を特定して時定数を算出します。その上で、マイコン上に離散化された一次IIRフィルタを実装するんです。
式にすると `val = alpha * new_val + (1 - alpha) * old_val` って感じですね。これを入れるだけで値の安定感が全く変わってくるので、ぜひ試してみてください！
