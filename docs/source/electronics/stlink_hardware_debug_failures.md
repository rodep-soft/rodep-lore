# ST-Linkとハードウェアデバッグにおける泥臭いトラブルシューティング

自作のSTM32搭載基板に初めて火を入れ、ST-Linkを繋いで書き込みを試みた瞬間、「Target not found」や「Can not connect to target」という非情なエラーに遭遇するのは、組み込み開発者にとって通過儀礼です。

本稿では、ST-Linkを用いたハードウェアデバッグ環境の構築において、回路設計のミスから設定の不備まで、現場で頻発する泥臭いトラブルとその解決策を詳細に解説します。

## 1. 書き込み失敗の代表的な原因と回路設計の罠

ST-Link（SWD: Serial Wire Debugプロトコル）による書き込みが失敗する原因の8割は、ハードウェアの物理的な結線や回路設計のミスに起因します。

### 1.1 NRST（リセットピン）の処理漏れ
STM32へのSWD接続には、最低限 `SWDIO`, `SWCLK`, `GND` の3本があれば理論上は書き込み可能ですが、実際の開発においては**`NRST`（ハードウェアリセット）**の接続が事実上必須です。

**よくある失敗**:
「SWDIOとSWCLKだけ繋げばいい」というネット記事を鵜呑みにし、NRSTピンを配線しなかった結果、マイコンがスリープモードに入ったり、SWDピンをGPIOとして再割り当てするコードを書き込んでしまった瞬間に、二度とST-Linkから認識されなくなる現象（文鎮化）に陥ります。

**対策**:
- ST-Linkの `NRST` ピンをSTM32の `NRST` ピンに必ず接続します。
- `NRST` ピンには、安定化のために**0.1μFのコンデンサをGND間に接続**（チャタリング防止）し、必要に応じて10kΩ程度のプルアップ抵抗を追加します。
- STM32CubeIDEやOpenOCDの設定で、Reset Modeを `Hardware Reset` または `Connect under reset` に設定することで、プログラム暴走時でも強制的にリセットをかけて書き込みが可能になります。

### 1.2 SWDピンの不用意な再割り当て
STM32では、SWDIO（PA13）とSWCLK（PA14）はリセット直後はデバッグピンとして機能しますが、ユーザープログラムでこれを通常のGPIO（例えばLED駆動やI2Cなど）として初期化してしまうと、プログラム起動直後にデバッガとの通信が切断されます。

```c
// 致命的な失敗例：PA13, PA14をGPIO出力にしてしまう
GPIO_InitStruct.Pin = GPIO_PIN_13 | GPIO_PIN_14; 
GPIO_InitStruct.Mode = GPIO_MODE_OUTPUT_PP;
HAL_GPIO_Init(GPIOA, &GPIO_InitStruct);
// これが実行された瞬間、ST-Linkはマイコンを見失う
```

この状態に陥った場合、前述の `Connect under reset` 設定を用いて、プログラムが起動する前のリセット期間中に書き込みをねじ込むしか復旧方法がありません。ピンアサインを設計する際は、PA13とPA14は「絶対に」他の用途と兼用しない設計が鉄則です。

### 1.3 VDDAとVSSAの未接続
ADCを使用しないプロジェクトであっても、マイコンのアナログ電源ピン（`VDDA`）とアナロググラウンド（`VSSA`）を未接続にしてはいけません。
内部のPLL（クロック生成回路）やパワーオンリセット（POR）回路がVDDAの電位に依存している品種（STM32F4など）があり、ここが浮いているとマイコン自体が正常に起動せず、ST-Linkからも全く認識されません。
ADCを使わなくとも、VDDAはVDDに、VSSAはGNDに必ず接続してください。

## 2. ST-Link V2 と V3 の仕様差異によるトラブル

安価な中華製ST-Link V2クローン（USBメモリ型のもの）と、公式のST-Link V3（またはNucleoボード内蔵のST-Link）では、挙動に大きな違いがあります。

### 2.1 電圧レベルの不一致
公式のST-Linkには `T_VCC`（ターゲット電圧検知ピン）があり、ターゲット基板のVDD電圧（例えば3.3V）を読み取って、SWD通信の電圧レベルを自動で合わせる機能があります。
しかし、クローン製品の多くはこのピンが機能しておらず、常に3.3Vで信号を出力します。もしターゲット基板が1.8V駆動であった場合、過電圧でSTM32のピンを破壊する恐れがあります。

### 2.2 通信速度の限界
ST-Link V2ではSWDのクロック（SWCLK）を最大4MHz程度まで上げられますが、ジャンパワイヤの配線が長い（20cm以上）場合、波形が鈍ってしまい `通信エラー（JTAG/SWD DP abort）` が発生します。
ST-Link V3は最大24MHzという高速通信が可能ですが、これは基板上のインピーダンスコントロールされた配線が前提です。自作基板でブレッドボードや長いワイヤを使っている場合は、デバッガの設定画面で**SWDクロックを1MHz〜2MHz程度に意図的に下げる**ことで、安定してデバッグできるようになります。

## 3. アナログ的トラブル：電源ノイズとブラウンアウト

ST-Linkは認識されるが、プログラムを実行していると途中で勝手にリセットがかかる、あるいは変数の中身がデバッガ上で突然「???」になる、といった怪奇現象は、大半が電源の品質に起因します。

### 3.1 バイパスコンデンサ（パスコン）の不足
STM32の各VDDピン（通常3〜4箇所あります）の「直近（数ミリ以内）」に**0.1μFのセラミックコンデンサ**が配置されていないと、マイコン内部でデジタル回路がスイッチングする瞬間に電圧が局所的に降下します。
これが原因でブラウンアウトリセット（BOR）がトリガされ、不可解な再起動を繰り返します。
すべての電源ピンに必ずパスコンを配置することは、デジタル回路設計の一丁目一番地です。

### 3.2 モータ駆動時の電源降下
ロボット制御基板などで、モータの起動時（突入電流発生時）にST-Linkのデバッグセッションが切断される現象があります。
これは、モータが一時的に大電流を引くことで基板全体の電圧が低下し、STM32がリセットされるか、あるいはST-Linkの通信回路が誤動作するためです。
対策として、マイコン用の3.3Vを生成するLDOの入力側に大きな電解コンデンサ（100μF〜470μF等）を追加し、モータ系の電源ラインとマイコン系の電源ラインを物理的に離す（またはLCフィルタを入れる）レイアウト設計が求められます。

## まとめ

ハードウェアデバッグにおけるトラブルは、「コードが間違っている」ことよりも「電気が正しく流れていない」ことに原因があるケースが圧倒的に多いです。
ST-Linkが繋がらない、あるいはデバッグが安定しないときは、画面上のエラーメッセージを睨みつけるのを一旦やめ、オシロスコープやテスターを手に取り、VDDピンの電圧、NRSTピンの波形、SWDラインのプルアップ状態といった「物理層」を疑うことが、解決への最短ルートとなります。
